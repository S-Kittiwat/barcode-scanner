# DocScan — โมดูลร่วมและวิธีนำไปใช้

ชุดนี้แก้สามอย่างที่ปิดความเสี่ยง "ย้อนกลับไม่ได้" ของระบบ
และทำให้การแก้ครั้งต่อ ๆ ไปถูกลง เพราะแก้ที่เดียวมีผลทุกหน้า

```
js/date.js    แปลงวันที่          — เดิมซ้ำอยู่หลายไฟล์
js/csv.js     ข้อมูลอ้างอิง        — ตัวอ่านใหม่ + ชั้นตรวจสอบความถูกต้อง
js/api.js     คุยกับ GAS          — timeout, retry, กันข้อมูลซ้ำ, อัปโหลดเป็นชุด
js/store.js   เก็บในเครื่อง       — งานค้าง, คิวรอส่ง, ข้อมูลอ้างอิง
gas/Code.gs   ฝั่งเซิร์ฟเวอร์      — upsert ตาม client_id
API.md        สัญญาระหว่างสองฝั่ง
test/         26 เทสต์ ผ่านทั้งหมด
```

รันเทสต์: `npm test` (ใช้ `node --test` ที่ติดมากับ Node ไม่ต้องลงอะไรเพิ่ม)

## สิ่งที่ค้นพบระหว่างทำ และเปลี่ยนการออกแบบ

### เลขเอกสารที่ออกเรียงลำดับ ทำให้การตรวจกับรายการอ้างอิงอ่อนกว่าที่คิด

ตอนแรกผมประเมินว่า "เทียบกับรายการอ้างอิง" คือชั้นตรวจสอบที่แข็งที่สุด
เทสต์ทำให้เห็นว่าไม่จริงทั้งหมด — จากเลข T ในไฟล์ตัวอย่างเพียง 8 ใบ
**มีถึง 8 คู่ที่ต่างกันแค่หลักเดียว**

```
T9648565 ~ T9648564      T9648551 ~ T9648550
T9648559 ~ T9648551      T9648551 ~ T9648521
T9648559 ~ T9648550      T9648523 ~ T9648522
T9648523 ~ T9648521      T9648522 ~ T9648521
```

แปลว่าถ้า OCR อ่านผิดหนึ่งหลัก ค่าที่ได้มีโอกาสสูงที่จะไป**ตรงกับเอกสารจริงอีกใบ**
แล้วผ่านการตรวจไปเงียบ ๆ ทั้งที่เป็นคนละใบ — ซึ่งแย่กว่าอ่านไม่ออกมาก
เพราะอ่านไม่ออกยังมีคนเห็น แต่อันนี้เข้า Sheet ไปโดยไม่มีใครรู้

**ทางแก้ที่ใส่ไว้แล้ว**

1. `hasCollisionRisk()` — ค่าจาก OCR ที่มีเพื่อนบ้านต่างกันหลักเดียว จะไม่ผ่านอัตโนมัติ แม้จะพบในรายการ
2. `crossCheck()` — ยืนยันด้วยสองฟิลด์ที่อ่านจากคนละที่บนเอกสาร (เลข T กับเลข Company Name)
   ทั้งคู่ต้องชี้ไปแถวเดียวกัน โอกาสที่จะอ่านผิดสองที่แล้วบังเอิญตรงใบเดียวกันต่ำมาก
3. ค่าจาก**บาร์โค้ด**ไม่ติดเงื่อนไขนี้ เพราะ Code 39 มี checksum ในตัว ไม่เพี้ยนทีละหลักแบบ OCR

ผลคือ LOSCAM ต้อง OCR **สองฟิลด์** ไม่ใช่ฟิลด์เดียว — เพิ่มงานตอนทำ แต่จำเป็น

### บั๊กเดิมที่เทสต์จับได้

- `parseCSV` เดิม `split(',')` ตรง ๆ — ชื่อลูกค้า `CP Axtra Co., Ltd.` ทำให้ทั้งแถวเลื่อนคอลัมน์
- `parseDateInput` เดิมตรวจแค่ `1..31` — `31/02/26` ผ่านได้

## ขั้นตอนนำไปใช้

### 1. วางไฟล์

```
s-kittiwat.github.io/
├── js/{api,csv,date,store}.js
├── config.js
└── batch.html
```

### 2. แก้ฝั่ง GAS ก่อนเสมอ

**ต้องทำก่อนแตะหน้าเว็บ** ถ้าหน้าเว็บมี retry แต่ GAS ยังไม่ upsert จะกลายเป็นเครื่องผลิตข้อมูลซ้ำ

1. เพิ่มคอลัมน์ `client_id`, `updated_at`, `read_source`, `system_flag`, `human_edited`, `sampled`, `app_version` ในชีต `Items`
2. วางโค้ดจาก `gas/Code.gs` แล้วแก้ `FOLDER_ID`
3. ทดสอบ: ส่ง `updateItems` ด้วย `client_id` เดิมสองครั้ง → **ต้องได้แถวเดียว** ครั้งที่สองตอบ `updated`
4. Deploy เป็น **New version** (ถ้าเลือก Test deployment URL จะไม่เปลี่ยน คนอื่นยังใช้ของเก่า)

### 3. แก้ `batch.html`

```html
<script type="module">
  import { apiFetch, uploadBatch, newClientId } from './js/api.js';
  import { parseCSV, buildIndex, classify } from './js/csv.js';
  import { parseDateInput, toDisplayDate, toInputDate } from './js/date.js';
  import { makeDraftSaver, loadDraft, clearDraft } from './js/store.js';
  window.DocScan = { apiFetch, uploadBatch, newClientId, parseCSV, buildIndex,
                     classify, parseDateInput, toDisplayDate, toInputDate };
</script>
```

วางไว้**ก่อน** `<script>` ก้อนเดิม แล้วลบฟังก์ชันซ้ำออกจาก `batch.html`
(`parseCSV`, `searchCSV`, `parseDateInput`, `toDisplayDate`, `toInputDate`)

ใน `_makeRow()` เพิ่ม `client_id: newClientId()`
ใน `submitBatch()` เปลี่ยนไปใช้ `uploadBatch()` และส่ง `client_id` ไปกับทุก item

### 4. ตรวจก่อนปล่อยจริง

- [ ] ส่ง batch เดียวสองครั้ง → Sheet มีแถวเดียว
- [ ] ตัดเน็ตกลางคัน แล้วต่อใหม่ → ไม่มีแถวซ้ำ ไม่มีไฟล์ซ้ำใน Drive
- [ ] ทดสอบ 50 หน้า → นับจำนวนคำขอควรอยู่ราว 11 ครั้ง (เดิม 51)
- [ ] refresh กลางคัน → มีข้อความถามว่าจะทำงานค้างต่อไหม
- [ ] วันที่ `31/02/26` → ต้องถูกปฏิเสธ

## สิ่งที่ผู้ดูแลระบบต้องทำ

### ก่อนเริ่ม (ครั้งเดียว)

**เพิ่มคอลัมน์ในชีต `Items`** ตามข้อ 2 — ชื่อคอลัมน์ต้องตรงเป๊ะ เพราะโค้ดจับคู่ตามหัวคอลัมน์

**สำรอง Sheet ก่อนแก้อะไร** — File → Make a copy เก็บไว้ ถ้า upsert ผิดพลาดจะได้ย้อนได้

**ตัดสินใจเรื่องฟิลด์ที่สองของ LOSCAM** — ต้องยืนยันว่าเลข Company Name (`260105632`)
ตรงกับคอลัมน์ไหนในข้อมูลอ้างอิง ถ้าไม่มีคอลัมน์นี้ การยืนยันสองฟิลด์จะใช้ไม่ได้
และ LOSCAM จะต้องให้คนตรวจทุกใบ — **ข้อนี้ต้องเช็คก่อนลงมือ**

**เลิกใช้ `latest` ในลิงก์ GAS** — ทุกครั้งที่ deploy ให้ตั้งเป็น version ที่ระบุชัดเจน
จะได้ย้อนกลับได้เมื่อของใหม่มีปัญหา

### ทุกครั้งที่ปล่อยของใหม่

1. อัปเลข `VERSION` ใน `config.js` — และต้องแสดงบนหน้าจอด้วย
   เวลาคนโทรมาบอกว่าใช้ไม่ได้ จะได้รู้ว่าเขาใช้เวอร์ชันไหน สำคัญมากเมื่อมี Service Worker แล้ว
2. รัน `npm test` ให้ผ่านก่อน push
3. ทดสอบบน branch แยกก่อน merge เข้า main
4. **ห้ามปล่อยของใหม่ในวันใกล้เดดไลน์ MT**

### ทุกสัปดาห์

- เปิดชีต `ErrorLog` ดูว่ามี error ซ้ำ ๆ ไหม
- ดูสัดส่วน `human_edited` แยกตาม `read_source` และ `system_flag`
  - `system_flag=true` + `human_edited=true` มาก = ระบบชี้เป้าแม่น ดี
  - `system_flag=false` + `human_edited=true` **แม้แต่ใบเดียว** = ของผิดหลุดรอด ต้องเข้มเกณฑ์ทันที

### ทุกเดือน

- ตรวจว่ามีแถวที่ `client_id` ว่างไหม (ควรเป็นศูนย์หลังใช้ระบบใหม่)
- ประเมินอัตราการสุ่มตรวจ — ถ้าสะสมหลายร้อยใบแล้วไม่เคยพบของหลุดรอด ค่อยลดจาก 10% เป็น 5%
- ทบทวนว่าเลขเอกสารชุดใหม่ยังออกเรียงลำดับอยู่ไหม เพราะมีผลกับความเสี่ยงชนกันโดยตรง

### เมื่อมีคนแจ้งปัญหา

ถามสามข้อนี้ก่อนเสมอ: **เวอร์ชันอะไร** (มุมจอ) · **หน้าไหน** · **มีอะไรค้างในคิวไหม**
แล้วดู `ErrorLog` ตามเวลาที่แจ้ง

## สิ่งที่ยังไม่ได้ทำ (เรียงตามลำดับที่ควรทำต่อ)

1. Service Worker + ย้ายไลบรารีเข้า repo → เปิดโปรแกรมได้ตอนเน็ตล่ม
2. ตัวระบายคิว outbox → `store.js` เตรียมที่เก็บไว้แล้ว แต่ยังไม่มีตัวส่ง
3. ให้ GAS ตรวจสิทธิ์เอง → ตอนนี้กันสิทธิ์ฝั่งหน้าเว็บอย่างเดียว เปิด DevTools ก็ข้ามได้
4. แก้ `_extractPDFPage()` ที่โหลด PDF ใหม่ทุกหน้า
5. **แล้วค่อยเอา OCR เข้า** — อย่าเพิ่งทำก่อนข้อ 1–4 เสร็จ
